# 派工 Prompt 模板

搭配 `model-dispatch.md` 使用。`{...}` 是填空。每個模板已內建派工四件套（目標與動機／驗收條件／回報格式／時間預算）與回報合約，照抄後填空即可，不要刪驗收與回報段落。

每個模板區塊末尾都有一段「固定條款」（執行者分包禁令／不編造／時間預算），照抄時**必須連同固定條款一起抄**，勿刪。這段條款是 session 內唯一能約束 subagent 的機制（doctrine 改動對 subagent 是舊快照，見 model-dispatch.md §9）。

---

## 1. 搜尋／定位（subagent_type: `Explore`；純字串/檔名搜尋 haiku，預設 sonnet，需要判斷用 opus。Explore 沒有 Edit/Write/Agent 工具，分包禁令對它是結構保證）

```
在 {repo 或目錄} 找 {目標：符號/字串/設定/所有 call site}。
動機：{為什麼找，讓你判斷哪些結果相關}。

驗收條件：
- 每個結果都有 檔案:行號。
- 明確說明搜尋是否窮盡（用了什麼 pattern、掃了哪些目錄、排除了什麼）。

回報格式：
- 結果清單：檔案:行號 + 一行說明該處在做什麼。
- 若超過 30 筆：寫到 {scratchpad 路徑}，回傳路徑 + 前 10 筆摘要。
- 找不到：回報用過的每個搜尋 pattern 與範圍，不要猜測性結論。

固定條款：
- 你是執行者：不得把任務切塊分包、不得外包判斷；只可派機械性求證查詢（規格明確、答案唯一、結果親自檢核、禁其再派）。覺得該拆，把建議拆法寫進回報，由主對話決定。
- 找不到或做不到就直說＋已嘗試的方法，不要編造。長內容寫到檔案回傳路徑，不要貼全文。
- 時間預算 {量級}：超過 ~{N} 次工具呼叫仍未收斂，停下回報部分結果與卡點。
```

## 2. 實作（model: sonnet；跨模組或設計含糊時用 opus。理解住在對話裡 → `subagent_type: fork`，此時 model 由父對話決定、本模板的「既有慣例」段可省；否則 fresh general-purpose）

```
目標：{要實作什麼，一句話}。
動機：{為什麼要做，上層需求是什麼}。
範圍：{要動的檔案/模組；明確列出「不要動」的東西，特別是對外介面}。
既有慣例：{指出 1-2 個可參考的既有實作，檔案:行號}。

做法要求：
- 測試先行：先寫測試建 baseline，再改實作（見 ~/.claude/doctrine/engineering.md）。
- 測試不可行時：停下來回報原因，不要跳過。

驗收條件：
- {具體行為：輸入 X 得到 Y}。
- 全部測試通過：實跑 {測試命令}，貼結果摘要。
- 未修改範圍外的檔案。

回報格式：
- 結論一段 + 改動檔案清單（檔案:行號）+ 測試輸出的關鍵行。
- 有任何跳過或未驗的事項必須列出。

固定條款：
- 你是執行者：不得把任務切塊分包、不得外包判斷；只可派機械性求證查詢（規格明確、答案唯一、結果親自檢核、禁其再派）。覺得該拆，把建議拆法寫進回報，由主對話決定。
- 找不到或做不到就直說＋已嘗試的方法，不要編造。長內容寫到檔案回傳路徑，不要貼全文。
- 時間預算 {量級}：超過 ~{N} 次工具呼叫仍未收斂，停下回報部分結果與卡點。
```

## 3. 重構（model: sonnet；牽動架構用 opus）

```
目標：把 {對象} 重構為 {目標形態}。
動機：{現在的痛點}。
硬限制：對外行為不變（API、routes、response 格式、錯誤碼）。發現重構「順便」需要改對外行為 → 停下來回報，不要自行決定。

做法要求：
- 先跑既有測試建 baseline，記錄結果；沒有測試就先補特徵測試（characterization test）再動手。
- 分小步進行，每步保持可編譯、測試綠。

驗收條件：
- baseline 測試在重構後全數通過，結果與重構前一致。
- {額外目標：如某類別行數/依賴數下降}。

回報格式：
- baseline 前後的測試結果對照 + 改動摘要（檔案:行號）。
```

## 4. 研究（model: sonnet；結論要拿來做高風險決策時用 opus 或加派第二個獨立 agent 交叉比對）

```
問題：{要回答什麼}。
動機：{答案會拿來決定什麼}。
來源優先序：{codebase / 官方文件 / 網路搜尋}，每個結論標註來源。

驗收條件：
- 每個結論附證據（檔案:行號、文件 URL 與段落、命令輸出）。
- 區分「查證過的事實」與「你的推論」，分開標示。
- 查不到的部分明確標「未查到」，不要用推測填補。

回報格式：
- 結論先行（3-5 句），證據清單在後。
- 超過一頁的完整報告寫到 {路徑}，回傳路徑 + 結論摘要。
```

## 5. 審查／驗收（model: opus；必須是沒參與實作的 fresh agent。**先分級**：可逆＋有可重跑的客觀檢核＋不動對外介面的低風險變更，實跑檢核即驗證，不派本模板——見 model-dispatch.md §8）

```
對象：{diff / 檔案清單 / 某 agent 的產出}。
你的立場：試著推翻它。你的任務是找出它「不能過」的理由，找不到才算通過。不要複述它做了什麼。

檢查清單：
- 驗收條件逐條實際驗證：{列出原任務的驗收條件}。程式碼用 {測試命令} 實跑；檔案用 read-back。
- 對外行為是否被改動（API、response 格式、錯誤碼）。
- 測試是否 tautological 或 over-mocked（見 ~/.claude/doctrine/engineering.md）。
- 有沒有被默默跳過的步驟。

回報格式：
- 結論：PASS / FAIL / PASS-WITH-NOTES（三選一，放第一行）。
- FAIL：每個問題附 檔案:行號 + 具體失敗情境（什麼輸入會出什麼錯）。
- PASS：列出你實際執行過的驗證動作與輸出證據，「看起來沒問題」不是證據。

固定條款：
- 你是執行者（verifier 也一樣）：不得把任務切塊分包、不得外包判斷；只可派機械性求證查詢（規格明確、答案唯一、結果親自檢核、禁其再派）。覺得該拆，把建議拆法寫進回報，由主對話決定。
- 找不到或做不到就直說＋已嘗試的方法，不要編造。長內容寫到檔案回傳路徑，不要貼全文。
- 時間預算 {量級}：超過 ~{N} 次工具呼叫仍未收斂，停下回報部分結果與卡點。
```

## 使用備註

- 升級重派時，在模板最上方加一段「失敗軌跡」：原始目標、每次嘗試的做法、實際輸出/錯誤原文、猜測的卡點。
- 獨立子任務並行派：同一個訊息裡發多個 Agent 呼叫（平面化直接派 N 個，不派 coordinator——見 model-dispatch.md §2）。使用者一次給多件事：先 TaskCreate 全部，再同訊息派出，TaskList 清完才結束 turn（§1）。
- 審查 agent 與實作 agent 不能是同一個對話延續（SendMessage 給原 agent 不算 fresh）。
- 預期 1-2 分鐘內完成、下一步立刻要用結果 → `run_in_background: false` 同步執行；其餘背景並行，等待期間不 sleep 不輪詢（model-dispatch.md §5）。
