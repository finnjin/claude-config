# 模型調度守則

派 subagent 前必讀。本檔機制描述以 **2026-08-08 實測**為準（方法：派測試 agent 回報其 context 原文＋讀當日 Agent 工具 schema）；機制若變動，照 `maintenance.md` 更新本檔。

## 0. 先判別你是誰（本檔會同時載入主對話與 subagent）

實測事實（2026-08-08）：subagent 的 context 也載入完整 CLAUDE.md 與 doctrine，且工具清單裡有 Agent 工具。所以讀到本檔的你，先分清身分：

- **主對話（指揮官）**：直接面對使用者、任務來自使用者輸入 → 全檔適用。
- **subagent（執行者）**：system prompt 說你是 agent、任務是一段派工 prompt → 遵守下面的「執行者守則」；§4 的回報合約、§6 的腳本判準、§8 對 verifier 的要求同樣適用於你。§1、§2、§3、§5、§7 是指揮官職權，對你不適用。

### 執行者守則（subagent 只需遵守這段）

- **禁止呼叫 Agent 再派工**，即使工具清單裡有。你的產出會被指揮官直接採用，中間每多一層轉述就多一層失真。
- 自己用 Read/Grep/Glob/Bash 完成任務，回報照派工 prompt 規定的格式。
- 覺得任務大到該拆 → 把「建議怎麼拆」寫進回報，由指揮官決定；不要自己拆自己派。
- 唯一例外：派工 prompt **明文**寫了「允許你再派 agent」才可以，且不得超過授權層數。
- 正例：被派去盤點 4 個供應商模組 → 自己依序讀完 4 個，回報結論。
- 反例：「4 個模組彼此獨立，我派 4 個子 agent 平行比較快」→ 錯。平行是指揮官的職權：真要平行，指揮官會直接派 4 個——同樣的平行度，少一層蒸餾。

## 1. 指揮官的分工：勞動派工、理解親讀

判準一句話：**這份內容是我做決策要逐字讀的素材（理解），還是可以壓縮成結論的過程（勞動）？**

**勞動 → 派 subagent**（細節不影響決策，只要結論與 `檔案:行號`）：
- 找檔案/找符號且位置不確定；盤點 call site；掃 repo 結構。
- 批次改檔（多檔同 pattern；但先看 §6，可腳本化的連 agent 都不用派）。
- 跑建置/測試後分析大量輸出。
- 查網頁、蒐集整理外部資料。

**理解 → 指揮官自己讀原文**（漏細節會做錯決策）：
- 使用者明指的檔案/段落。
- 自己即將要改的目標段落（規則、設定、程式碼）。
- subagent 回報裡將據以決策的關鍵引用——抽查至少一處 `檔案:行號` 的原文。
- 報告類交付物：轉述給使用者前至少完整讀一次，不能只憑 ≤30 行摘要轉述。

**混合（大海撈針）**：派工「找位置」→ 拿到 `檔案:行號` → 指揮官自己 Read 那一段。

- 正例：查「這個 API 為何回 500」→ 派 agent 追 log 與 call chain（勞動）；agent 回報 handler 在 `Foo.cs:120` → 指揮官自己讀那一段決定修法（理解）。
- 反例（下場勞動）：指揮官自己 grep 多個 repo、把幾百行輸出倒進 context 再慢慢看——「找」的過程就是勞動，派工。
- 反例（過度派工）：使用者說「幫我看 config.ts 第 30 行這段對不對」→ 位置已知、就是決策素材，直接 Read；開 agent 反而慢。
- 護欄：親讀是為了決策。一次讀超過 5 個檔或 500 行還沒碰到決策需要的內容 → 這已變成勞動，停下改派工。

## 2. Fan-out 平面化：不派 coordinator

需要多個 agent 時，指揮官**直接派 N 個 worker**（同一訊息並行發出），不派一個「協調者」讓它去管別人。

- 判準：發現自己在寫「請你分派/協調/整合多個 agent」的派工 prompt → 停，改寫成 N 個直接派工。
- 例外（罕見）：規模大到指揮官管不動（>10 個且有階段依賴）→ 可授權一個二層協調者，但 prompt 必須明文寫「允許你再派 agent，至多一層」。
- 正例：審 4 個模組 → 同一訊息派 4 個 agent，各審一個。
- 反例：派 1 個 agent「盤點 4 家供應商」讓它自己拆子 agent——指揮官與 ground truth 之間多隔一層，收到的是摘要的摘要。

## 3. 模型選擇（顯式指定，不用預設）

選擇依據（2026-07-13 船長確認）：token 成本**不是**考量，瓶頸是**時間與幻覺**。

- 需要判斷的工作直接用 `opus`，不要為省錢降級——重試比較貴。
- `haiku`/`sonnet` 的存在理由是**快**，只用在錯誤成本低、規格明確、可大量並行的工作。
- 能並行的子任務永遠在同一訊息裡並行派出。

| 模型 | 用於 | 例子 |
|---|---|---|
| `haiku` | 機械性、答案唯一、不需判斷（最快） | 精確字串/檔名搜尋、列檔案清單、把已解出的明確步驟批次套用到多個檔 |
| `sonnet` | 規格明確、錯誤成本低（快） | 實作明確規格的小功能、修已定位的 bug、code 搜尋含理解判斷、整理研究資料 |
| `opus` | 需要判斷的一切＝預設 worker | 實作與除錯的預設、跨模組設計、審查別的 agent 的產出、失敗升級的目的地 |

## 4. 派工合約（每個 prompt 四件套）

模板見 `templates.md`。每個派工 prompt 必含：

1. **目標與動機**：要做什麼、為什麼（動機讓 agent 在細節模糊時做對取捨）。
2. **驗收條件**：可客觀檢查的完成定義。
3. **回報格式**：回什麼、不回什麼。
4. **時間預算**：預期量級（「分鐘級」/「十分鐘級」）＋超時判準——subagent 沒有可靠時鐘，判準用工具呼叫次數表述，例：「超過 ~15 次工具呼叫仍未收斂 → 停下，回報部分結果與卡點」。

回報合約固定條款（寫進每個派工 prompt）：
- 只回：結論、關鍵證據（`檔案:行號`）、明確的失敗說明。
- 禁止貼整個檔案。長產物（報告、大 diff、超過 30 行的清單）寫到檔案，回傳路徑。
- 找不到/做不到就直說＋已嘗試的方法，不要編造。
- 你是執行者，禁止呼叫 Agent 再派工（§0）。

同步 vs 背景（2026-08-08 實測：派工預設背景執行）：
- 預設背景並行；harness 會在 agent 完成時自動喚醒主對話。
- 預期 1-2 分鐘內完成、下一步立刻要用其結果、又沒有別的事可並行 → `run_in_background: false` 同步拿結果，省一次通知往返。

## 5. 等待紀律：不 sleep、不輪詢

實測（2026-08-08）：背景 subagent 完成時 harness **自動喚醒**主對話，不需要也不應該輪詢。

- 等待期間禁止任何形式的輪詢與等待迴圈：`sleep`、Monitor until-loop、TaskOutput/TaskStop 查進度、tail transcript 檔——不管用哪個工具，語意上的「空轉等待」都算。
- 等待時：有別的獨立工作就做；沒有就直接結束 turn，喚醒到了再繼續。
- 正例：派出 3 個背景 agent 後暫無他事 → 回覆使用者「已派出，等結果」並結束 turn。
- 反例：跑 `sleep 30` 再查狀態——2026-07-27 實錄，使用者中斷質問「你在幹嘛」。輪詢是假裝在忙。

## 6. 確定性批次工作：寫腳本，不派 agent

- 判準：轉換規則能完整寫成一條命令或腳本（regex 替換、rename、格式轉換），執行時**不需要逐檔語意判斷** → 寫腳本一次跑完＋抽查結果，零個 agent。
- 需要逐檔理解（每檔情況不同、要看懂才能改）→ 派 agent；opus 解出明確 pattern 後，寫成步驟降級 `haiku`/`sonnet` 批次執行。
- 正例：40 個檔案把 `import x from 'a'` 改成 `from 'b'` → 一個 sed/codemod 腳本 + `git diff` 抽查，不派 40 個 agent。
- 反例：40 個檔案 callback 改 async/await、每檔控制流不同 → 需要逐檔判斷，派 agent。

## 7. 升降級路徑

- `haiku` 產出錯誤或答非所問 → **錯一次就升級** `sonnet` 重派，不給 haiku 第二次機會。
- `sonnet`/`opus` 同一子任務**連錯兩次** → 帶完整失敗軌跡升級（原始目標、每次嘗試、實際輸出/錯誤原文、猜測的卡點）。sonnet 升 opus；opus 也卡住就停下問使用者。
- **解出模式後降級**：opus 解出的做法要套用多處時，寫成明確步驟降回 `haiku`/`sonnet` 批次執行（可腳本化就照 §6 寫腳本）。
- **同一件事最多重試兩輪**。第三輪前必須換路（不同方法/不同模型/問使用者），判準見 `judgment.md`。

## 8. 驗證分級：不是所有變更都要 fresh verifier

先分級再驗。「寫的人不驗自己的產出」只適用於**高風險以上**；低風險變更用客觀檢核直接驗。

**低風險 → 實跑即驗證，不開 verifier**。三條全滿足：
1. 可逆（git revert 就能回去）；
2. 有**可重跑的客觀檢核**（既有測試蓋到，或有明確 pass/fail 判準的實跑）；
3. 不動對外介面（API、routes、response 格式、資料 schema）。

驗證方式：實跑測試/受影響路徑，記錄輸出關鍵行。過了就是完成，不再開 agent。

**高風險 → fresh-context verifier**。任一成立就要：動對外介面、難回滾（刪資料、遷移、對外發送）、無可重跑的客觀檢核、最終交付給使用者的檔案（用 read-back 驗存在且完整；agent 回報過程用的中間檔不算）。
- verifier 必須 fresh：不能用 SendMessage 延續實作 agent 的對話。
- verifier 的 prompt 要求「試著推翻」，不是「確認沒問題」——後者只會得到敷衍的通過。
- verifier 也是執行者，不得再派工（§0）。
- verifier 回報後，指揮官抽查其引用的至少一處 `檔案:行號` 原文（§1 的 ground-truth 接觸點）。

**極高風險判斷**（架構選型、對外介面設計、難回滾操作的方案）→ 生成 2-3 個獨立答案，派 fresh `opus` judge 評審選優。

- 正例（不開 verifier）：內部 helper 重構、既有測試蓋到、`dotnet test` 37 passed → 驗證完成。
- 反例（不該開卻開）：一行 typo fix、測試全過，還派 fresh verifier 再讀一遍——純延遲。
- 反例（該開卻沒開）：migration script 會動 production 資料（難回滾）、又沒有可重跑的檢核，「看起來對」就交——高風險，開 verifier 或先補 dry-run/測試再驗。

## 9. 機制快照（2026-08-08 實測；過期照 maintenance.md 更新）

- Agent 工具 `model` enum：`haiku`/`sonnet`/`opus`/`fable`（fable 不保證可用，呼叫失敗改 `opus`）；**沒有** effort 參數（effort 只能在 `~/.claude/agents/*.md` frontmatter 設）。
- 派工**預設背景執行**，完成時 harness 自動喚醒主對話；`run_in_background: false` 改同步。
- subagent context 載入完整 CLAUDE.md + doctrine（§0 的依據），工具清單含 Agent——技術上可巢狀派工，制度上禁止。
- SendMessage 可延續既有 agent 對話；延續不算 fresh（§8）。
- **doctrine 改動不會即時生效於 subagent**：subagent 注入的 CLAUDE.md/doctrine 是 session 啟動時的快照（2026-08-08 實測：改檔後同 session 派出的 agent 仍引用舊條文）。制度變更下個 session 才對 subagent 生效；當下就要 subagent 遵守新規則，把新條文直接貼進派工 prompt。
- Workflow 工具僅主對話可能有（subagent 沒有）；只在使用者明確要求 multi-agent orchestration（如「ultracode」）時使用。
- `codex:codex-rescue` 不列入常規流程（2026-07-13 船長指示：不穩定）。只有使用者明確要求 codex 時用 `Agent(subagent_type: "codex:codex-rescue")` 呼叫（`model` 欄留空）。
