# 模型調度守則

派 subagent 前必讀。本檔機制描述以 **2026-08-08 實測**為準（方法：派測試 agent 回報其 context 原文＋讀當日 Agent 工具 schema）；機制若變動，照 `maintenance.md` 更新本檔。

## 0. 先判別你是誰（本檔會同時載入主對話與 subagent）

實測事實（2026-08-08）：subagent 的 context 也載入完整 CLAUDE.md 與 doctrine，且多數型別的工具清單裡有 Agent 工具（`Explore` 例外）。所以讀到本檔的你，先分清身分：

- **主對話（指揮官）**：直接面對使用者、任務來自使用者輸入 → 全檔適用。
- **subagent（執行者）**：system prompt 說你是 agent、任務是一段派工 prompt → 遵守下面的「執行者守則」；§3 的模型選擇、§4 的回報合約、§5 的等待紀律（你派的子任務也適用）、§6 的腳本判準、§8 對 verifier 的要求、§9 的 schema 優先（僅「照 schema 行動」；更新 doctrine 是主對話職權）同樣適用於你。§1、§2、§7 是指揮官職權，對你不適用。

### 執行者守則（subagent 只需遵守這段）

派工 prompt 有明文授權或禁止時，以 prompt 為準。沒有明文時，分包看**交付物型態**，不看層數。目標是每個 agent 的 context 都保持精煉——把 tool 噪音吸收在葉節點，不讓任何一個節點吞下超過它能保持清醒的範圍。

**可分包**——子任務的交付物是可親核的事實或結果：
1. **機械性求證查詢**：規格明確、答案唯一、錯了一眼看得出（精確字串/檔名搜尋、列 call site、確認檔案含某內容）。用 `haiku` 或 `sonnet`。
2. **帶引文合約的 findings 掃描**：條件是拆法在你**偵察後才浮現**——「不讀任何檔案、只憑派工 prompt 就列得出子任務清單」屬派工前已知，那是指揮官平面派的職權，寫進回報請指揮官重派，不自己當中間層。每個子 prompt 帶起點與回報合約（結論附 `檔案:行號`）。
3. **可壓縮理解的接力**：你已讀懂、且能把該懂的壓進 20 行以內的 brief＋`檔案:行號` 起點（與 §1 的 brief 門檻同一把尺）→ 可派 fresh agent 照 brief 動手。

**不可分包**：壓不進 brief 的理解（隱性取捨多、caveat 越寫越多、行動方得重建一遍判斷才能動手）——自己做，或把理解+行動整包派出，讓同一個 agent 自己讀懂自己改。判別時機就在寫子 brief 的當下，行數只是上限、行為判準優先：行動方不需「視情況再判斷」→ 可接力；反之整包。

**每條派工邊的不變量**（深度不設上限，靠這些守住）：
- 派工者寫得出窄 brief（目標、驗收、起點）——寫不出代表自己還不懂，不該派。
- 子回報帶 `檔案:行號` 引文或驗證輸出；派工者親核抽查至少一處，不得直接轉抄成自己的回報結論。
- 你的回報說明抽查了哪些子引文，讓親核鏈對上層可見（引文能穿透層數，負面宣稱「掃過了沒發現」不能——用可見的親核鏈補）。

- 正例：實作 agent 讀完模組、形成假說「X 只被 Y 呼叫」→ 派一個 haiku 全 repo 精確搜尋 X 的 call site 求證。
- 正例：被派「全分支掃八類 pattern」，偵察後發現按 pattern 拆最合理 → 直接拆子 agent 各掃一類，各帶引文合約，彙整時抽查子回報引文。
- 反例：被派「盤點 7 個區域的現況」，拆法（by 區域）一開始就明顯 → 建議拆法寫進回報請指揮官平面派，不自己當中間層。
- 反例：讀懂複雜模組後把大概的理解轉述給另一個 agent 去改——理解壓不進 brief 就掉 nuance，自己改或整包派。

## 1. 指揮官的分工：看動詞，不看大小

主對話是運籌角色，判準是**動作的性質**：

| 動作 | 誰做 | 機制 |
|---|---|---|
| **探索**：找／查／追——不知道答案或位置，要去找 | 派 | `subagent_type: Explore`（沒有 Edit/Write/Agent 工具，結構上不能巢狀；有 Bash，不等於唯讀）；純精確字串／檔名搜尋 `haiku`，預設 `sonnet`，需要判斷用 `opus` |
| **執行**：改／跑／修——做了要跑東西才知道對不對（有回饋迴圈） | 派 | 理解住在對話裡（剛與使用者敲定的需求、取捨）→ `fork`；理解住在檔案裡或可用 `檔案:行號` 指路 → fresh `general-purpose` + brief；要 fresh 眼睛（verifier）或指定模型 → fresh |
| **運籌**：定／寫規格／寫 brief／審結論／答使用者 | 自己 | — |

Read 只有三個合法用途：(a) 使用者指定的檔案或段落；(b) 審核 subagent 回報時抽查它引用的 `檔案:行號`；(c) 運籌素材的原文——計畫、findings、要轉述給使用者的交付物，限**文字產物**（plan.md / 報告），不含 source code（「auth 模組是我據以指揮的東西」不算）。**用 Read 去「找」就是探索**，派工。

唯一例外：一次 Edit、不需要跑任何東西確認的變更（文件 typo、改常數）→ 直接做。判準是「沒有回饋迴圈」，不是「小」：改完你會想跑一下或看輸出確認，就是有迴圈，「沒有測試」不等於沒有迴圈；整件事總共一次 Edit，出現第二次 Edit 就停下派工。

寫 brief 是運籌工作：目標、驗收、範圍、起點 `檔案:行號`（§4）。寫不出 20 行以內的 brief，代表還不夠懂這件事——先派探索拿起點，不是自己下場讀。跨多輪累積的理解（計畫、已查明的事實）落成檔案（scratchpad 的 plan.md / findings.md），fresh agent 與 verifier 讀同一份；主對話已跑過多輪修改迴圈之後，落檔再 fresh 派，不 fork。

**多任務**：使用者一次給 ≥2 件彼此獨立、各需一輪執行的事（同一次探索能一併回答的不算）→ 先 `TaskCreate` 全部 → 可平行的在**同一訊息**全部派出 → `TaskList` 沒清完不結束 turn。反例：inline 先做第一件，做完停下等使用者，第二件忘掉。

- 正例：「這個 API 為何回 500」→ 派 Explore 追 call chain（探索）；回報 handler 在 `Foo.cs:120` → 指揮官 Read 那一段（抽查回報引用）→ 寫 brief 派 fresh agent 修（執行）→ 收 diff 與測試輸出。
- 正例：使用者說「幫我看 config.ts 第 30 行這段對不對」→ Read 那一段回答；要判斷對不對得追這個值在別處怎麼被用 → 那是探索，派 Explore，不順手多讀幾個檔。
- 正例：計畫是據以指揮的東西 → 指揮官自己讀；為了驗計畫去讀它碰到的 20 個檔 → 探索，派 verifier 收結論。
- 反例：「應該在 services 底下」就自己 grep 幾輪再 Read 三個檔——位置不確定就是探索，派 Explore。
- 反例：「只是改個 null check」自己 Edit 後跑測試、掛了再改——一跑測試就是回饋迴圈，派工。

## 2. Fan-out 形狀：拆法已知就平面派，未知就授權自拆

- 拆法在派工前已知（區域/項目列得出來）→ 指揮官**直接派 N 個 worker**（同一訊息並行發出），不派「協調者」——拆法已知時中間層只是多一層轉述。
- 拆法要偵察後才浮現 → 派一個 agent 並在 prompt 明文授權「偵察後可自行分包」，§0 的派工邊不變量照守——偵察過的 agent 拆得比指揮官準，且省一次「回報建議拆法 → 重派」的往返與冷啟動。明文授權不可省：subagent 載入的 doctrine 是 session 啟動時的舊快照（§9），prompt 是唯一即時生效的通道。
- 判準：寫得出「請你分派 N 個 agent 各做…」的 prompt，代表拆法你已經知道 → 改寫成 N 個直接派工。
- 正例：審 4 個模組 → 同一訊息派 4 個 agent，各審一個。
- 反例：派 1 個 agent「盤點 4 家供應商」讓它自己拆——拆法（by 供應商）派工前就知道，指揮官收到的是摘要的摘要。

## 3. 模型選擇（顯式指定，不用預設）

選擇依據（2026-07-13 船長確認）：token 成本**不是**考量，瓶頸是**時間與幻覺**。

- 需要判斷的工作直接用 `opus`，不要為省錢降級——重試比較貴。
- `haiku`/`sonnet` 的存在理由是**快**，只用在錯誤成本低、規格明確、可大量並行的工作。
- 能並行的子任務永遠在同一訊息裡並行派出。

| 模型 | 用於 | 例子 |
|---|---|---|
| `haiku` | 機械性、答案唯一、不需判斷（最快） | 精確字串/檔名搜尋、列檔案清單、把已解出的明確步驟批次套用到多個檔 |
| `sonnet` | 規格明確、錯誤成本低（快） | 實作明確規格的小功能、修已定位的 bug、code 搜尋含理解判斷、整理研究資料 |
| `opus` | 需要判斷的一切＝預設 worker | 實作與除錯的預設、跨模組設計、審查別的 agent 的產出、失敗升級的目的地 |

## 4. 派工合約（每個 prompt 四件套）

模板見 `templates.md`。每個派工 prompt 必含：

1. **目標與動機**：要做什麼、為什麼（動機讓 agent 在細節模糊時做對取捨）。
2. **驗收條件**：可客觀檢查的完成定義。
3. **回報格式**：回什麼、不回什麼。
4. **時間預算**：預期量級（「分鐘級」/「十分鐘級」）＋超時判準——subagent 沒有可靠時鐘，判準用工具呼叫次數表述，例：「超過 ~15 次工具呼叫仍未收斂 → 停下，回報部分結果與卡點」。

回報合約固定條款（寫進每個派工 prompt）：
- 只回：結論、關鍵證據（`檔案:行號`）、明確的失敗說明。
- 禁止貼整個檔案。長產物（報告、大 diff、超過 30 行的清單）寫到檔案，回傳路徑。
- 找不到/做不到就直說＋已嘗試的方法，不要編造。
- 你是執行者：可分包機械求證查詢與「偵察後才浮現的拆分」（子回報帶 `檔案:行號` 引文、親核抽查後才可彙整）；壓不進 brief 的理解不外包，自己做或理解+行動整包派（§0 執行者守則）。

**派工要窄、給起點**：subagent 時長的大宗是冷啟動自己掃 repo（2026-08 實測：指揮官直接派的 agent 時長 p90≈20+ 分鐘、context p90≈19 萬 tokens；巢狀層反而較短——問題在直接派工的範圍太寬，不在層數）。派工 prompt 給明確起點（已知的 `檔案:行號`、目錄範圍、可參考的既有實作），範圍劃窄；起點不知道就先派 Explore 拿，不是指揮官自己掃 repo 去找（§1）；預估十分鐘級以上的任務，先想能不能由指揮官拆成幾個窄任務平面派；拆法要偵察後才知道的，在 prompt 明文授權 agent 偵察後自拆（§2），不派一個 agent 硬吞全範圍。
- 正例：「查 X 的所有 call site，範圍 `src/Services/`，已知主要入口 `Foo.cs:120`」。
- 反例：「讀懂整個 repo 然後回答 X」——冷啟動全掃，十幾分鐘起跳，回報還稀釋。

同步 vs 背景（2026-08-08 實測：派工預設背景執行）：
- 預設背景並行；harness 會在 agent 完成時自動喚醒主對話。
- 預期 1-2 分鐘內完成、下一步立刻要用其結果、又沒有別的事可並行 → `run_in_background: false` 同步拿結果，省一次通知往返。

## 5. 等待紀律：不 sleep、不輪詢

實測（2026-08-08）：背景 subagent 完成時 harness **自動喚醒**主對話，不需要也不應該輪詢。

- 等待**背景 subagent** 期間禁止任何形式的輪詢與等待迴圈：`sleep`、Monitor until-loop、TaskOutput/TaskStop 查進度、tail transcript 檔——不管用哪個工具，語意上的「空轉等待 subagent」都算。本條只管等 subagent；等本地長命令（build、測試）照當下工具 schema 提供的機制處理（如背景執行＋自動喚醒），不受本條限制。
- 等待時：有別的獨立工作就做；沒有就直接結束 turn，喚醒到了再繼續。
- 正例：派出 3 個背景 agent 後暫無他事 → 回覆使用者「已派出，等結果」並結束 turn。
- 反例：跑 `sleep 30` 再查狀態。輪詢是假裝在忙。

## 6. 確定性批次工作：寫腳本，不派 agent

- 判準：轉換規則能完整寫成一條命令或腳本（regex 替換、rename、格式轉換），執行時**不需要逐檔語意判斷** → 寫腳本一次跑完＋抽查結果，零個 agent。
- 需要逐檔理解（每檔情況不同、要看懂才能改）→ 派 agent；opus 解出明確 pattern 後，寫成步驟降級 `haiku`/`sonnet` 批次執行。
- 正例：40 個檔案把 `import x from 'a'` 改成 `from 'b'` → 一個 sed/codemod 腳本 + `git diff` 抽查，不派 40 個 agent。
- 反例：40 個檔案 callback 改 async/await、每檔控制流不同 → 需要逐檔判斷，派 agent。

## 7. 升降級路徑

- `haiku` 產出錯誤或答非所問 → **錯一次就升級** `sonnet` 重派，不給 haiku 第二次機會。
- `sonnet`/`opus` 同一子任務**連錯兩次** → 帶完整失敗軌跡升級（原始目標、每次嘗試、實際輸出/錯誤原文、猜測的卡點）。sonnet 升 opus；opus 也卡住就停下問使用者。
- **解出模式後降級**：opus 解出的做法要套用多處時，寫成明確步驟降回 `haiku`/`sonnet` 批次執行（可腳本化就照 §6 寫腳本）。
- **同一件事最多重試兩輪**。第三輪前必須換路（不同方法/不同模型/問使用者），判準見 `judgment.md`。

## 8. 驗證分級：不是所有變更都要 fresh verifier

先分級再驗。「寫的人不驗自己的產出」只適用於**高風險以上**；低風險變更用客觀檢核直接驗。

**低風險 → 實跑即驗證，不開 verifier**。三條全滿足：
1. 可逆（git revert 就能回去）；
2. 有**可重跑的客觀檢核**（既有測試蓋到，或有明確 pass/fail 判準的實跑）；
3. 不動對外介面（API、routes、response 格式、資料 schema）。

驗證方式：實跑測試/受影響路徑，記錄輸出關鍵行。過了就是完成，不再開 agent。

**高風險 → fresh-context verifier**。任一成立就要：動對外介面、難回滾（刪資料、對外發送）、無可重跑的客觀檢核、最終交付給使用者的檔案（用 read-back 驗存在且完整；agent 回報過程用的中間檔不算）。

**驗不到的不硬驗**：開 verifier 的前提是存在 agent 執行得了的檢核。agent 碰不到的東西（production 資料實態、外部系統的真實行為）不因風險高就開 verifier 儀式性地「驗」——標註「未驗：X，依賴 {CI/staging/人工 review}」交出去（judgment.md §5：誠實的未驗優於假裝驗過）。
- 正例：migration script——語法與慣例 CI 會擋、資料正確性 agent 驗不到 → 不開 verifier，標註未驗與依賴的管道。
- verifier 必須 fresh：不能用 SendMessage 延續實作 agent 的對話。
- verifier 的 prompt 要求「試著推翻」，不是「確認沒問題」——後者只會得到敷衍的通過。
- verifier 也適用 §0 執行者守則。
- verifier 回報後，指揮官抽查其引用的至少一處 `檔案:行號` 原文（§1 的 ground-truth 接觸點）。

**極高風險判斷**（架構選型、對外介面設計、難回滾操作的方案）→ 生成 2-3 個獨立答案，派 fresh `opus` judge 評審選優。

- 正例（不開 verifier）：內部 helper 重構、既有測試蓋到、`dotnet test` 37 passed → 驗證完成。
- 反例（不該開卻開）：一行 typo fix、測試全過，還派 fresh verifier 再讀一遍——純延遲。
- 反例（該開卻沒開）：改了 API response 格式、沒有測試蓋到，「看起來對」就交——動對外介面＋無可重跑檢核，開 verifier。

## 9. 機制快照（2026-08-08 實測；過期照 maintenance.md 更新）

- **Schema 優先**：當下 session 的工具 schema 與本快照矛盾時，一律以 schema 為準行動，不要照舊條文對抗工具（重試不存在的參數、堅持已改變的預設）。「照 schema 行動」所有人適用；「照 maintenance.md 更新本節」只有主對話做——subagent 發現矛盾時寫進回報，不得自行改 doctrine 檔。**新增**機制事實中 schema 不自帶的（工具說明每 session 看得到的不記）一律寫進本節；其他章節出現的工具名與參數是判準的示例，與本節或當下 schema 矛盾時以後者為準，修正時改本節即可、不刪章節內容。工具面可能因位置而異（主對話與 subagent 的清單不同），以「自己當下看得到的 schema」為準。
- Agent 工具 `model` enum：`haiku`/`sonnet`/`opus`/`fable`（fable 不保證可用，呼叫失敗改 `opus`）；**沒有** effort 參數（effort 只能在 `~/.claude/agents/*.md` frontmatter 設）。
- 派工**預設背景執行**，完成時 harness 自動喚醒主對話；`run_in_background: false` 改同步。
- subagent context 載入完整 CLAUDE.md + doctrine（§0 的依據），多數型別工具清單含 Agent（`Explore` 沒有）——巢狀派工的合法性照 §0 的交付物型態判準。
