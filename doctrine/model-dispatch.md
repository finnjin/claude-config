# 模型調度守則

派 subagent 前必讀。本檔的機制描述以 2026-07 的 harness 實測為準，機制若變動，照 `maintenance.md` 更新本檔。

## 1. 指揮官不下場

主對話（指揮官）的 context 是最貴的資源，只放：使用者意圖、決策、各 subagent 的結論。
以下工作一律派 subagent，不自己做：

- 找檔案/找符號，且位置不確定（確定位置的單檔直接 Read，不用派）。
- 讀超過 3 個檔案，或任何「先讀懂這個模組」型任務。
- 掃 repo（grep 多處、盤點結構、找所有 call site）。
- 查網頁、讀文件。
- 批次改檔（同一 pattern 套多個檔案）。
- 跑建置/測試後需要分析大量輸出。

**不派的情況**（避免過度派工）：已知確切位置的單檔小修、直接 Read 不超過 3 個已知位置的檔案（與上方門檻一致）、和使用者的對話往來。派工本身有成本，幾次 Read 能解決的不要開 agent。

多個獨立子任務 → 同一個訊息裡發多個 Agent 呼叫，並行執行。

## 2. 派工三件套

每個派工 prompt 必含三件（模板見 `templates.md`）：

1. **目標與動機**：要做什麼、為什麼做（動機讓 agent 在細節模糊時做出對的取捨）。
2. **驗收條件**：可客觀檢查的完成定義（測試通過、檔案存在且含某內容、找到 N 個以上 call site 等）。
3. **回報格式**：明確規定回什麼、不回什麼。

## 3. 模型選擇（顯式指定，不用預設）

Agent 工具的 `model` 參數可用值：`haiku`、`sonnet`、`opus`。
（`fable` 在 enum 裡但未來 session 不保證可用；呼叫失敗就改用 `opus`。）
Agent 工具**沒有** effort 參數；effort 只能在自訂 agent 定義（`~/.claude/agents/*.md` frontmatter）裡設。
注意：`codex:codex-rescue` **不列入常規流程**（2026-07-13 船長指示：該 skill 不穩定）。只有使用者當下明確要求用 codex 時才用 `Agent(subagent_type: "codex:codex-rescue")` 呼叫（它不是 `model` 值，`model` 欄留空）。

選擇依據（2026-07-13 船長確認）：token 成本**不是**考量，瓶頸是**時間**。

- 需要判斷的工作直接用 `opus`，不要為省錢降級——省錢省不到瓶頸資源，重試反而更耗時。
- `haiku`/`sonnet` 的存在理由是**快**，只用在錯誤成本低、規格明確、可大量並行的工作。
- 時間是稀缺資源：能並行的子任務永遠在同一訊息裡並行派出。

| 模型 | 用於 | 例子 |
|---|---|---|
| `haiku` | 機械性、答案唯一、不需判斷（最快） | 精確字串/檔名搜尋、列檔案清單、格式轉換、把已解出的 pattern 批次套用到多個檔 |
| `sonnet` | 規格明確、錯誤成本低（快） | 實作明確規格的小功能、修已定位的 bug、code 搜尋含理解判斷、整理研究資料 |
| `opus` | 需要判斷的一切＝預設 worker | 實作與除錯的預設、跨模組設計、審查別的 agent 的產出、失敗升級的目的地 |

主對話可能提供 Workflow 工具（subagent 環境沒有；工具清單裡找不到就當作沒有，改用 Agent 並行派工）。它只有使用者明確要求 multi-agent orchestration（如「ultracode」「跑 workflow」）時才能用；平常用 Agent 工具就好。

## 4. 回報合約

寫進每個派工 prompt 的固定條款：

- 只回：結論、關鍵證據（`檔案:行號`）、明確的失敗說明（如果失敗）。
- 禁止把整個檔案內容貼回來。長產物（報告、大 diff、清單超過 30 行）寫到檔案，回傳路徑。
- 找不到/做不到就直說「找不到」＋已嘗試的方法，不要編造。

## 5. 升降級路徑

- `haiku` 產出錯誤或答非所問 → **錯一次就升級** `sonnet` 重派，不給 haiku 第二次機會。
- `sonnet`/`opus` 同一子任務**連錯兩次** → 帶完整失敗軌跡升級（給下一手：原始目標、每次嘗試做了什麼、實際輸出/錯誤訊息、你猜測的卡點）。sonnet 升 opus；opus 也卡住就停下問使用者。
- **解出模式後降級**：opus 解出的做法若要套用到多處，把做法寫成明確步驟，降回 `haiku`/`sonnet` 批次執行。
- **同一件事最多重試兩輪**。第三輪前必須換路（不同方法/不同模型/問使用者），判準見 `judgment.md`。

## 6. 驗證不自驗

寫的人不驗自己的產出。驗收一律派 **fresh-context agent**（不帶實作過程的偏見）：

- **檔案產出** → read-back：新 agent 讀檔，確認存在、完整、符合驗收條件。
- **程式碼** → 測試或實跑：新 agent 跑測試/實際執行，回報輸出原文，不接受「應該會過」。
- **高風險判斷**（架構決策、會影響對外介面、難以回滾的操作）→ 生成 2-3 個獨立答案，再派一個 fresh opus judge 評審選優。
- 驗收 agent 的 prompt 要求「試著推翻」而不是「確認沒問題」——後者會得到敷衍的通過。
