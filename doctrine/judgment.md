# 判斷力 Rubric

把「什麼時候該怎麼辦」寫成可核對的判準。每條附正例與反例。
觸發時機：要宣稱完成、卡住、猶豫要不要問使用者、懷疑方向錯了——先開本檔對照。

## 1. 何時該升級模型

出現任一訊號就升級，不要「再試最後一次」：

- 同一子任務已失敗兩次，且第二次的錯和第一次**本質相同**（不是新的錯，是同一個坑）。
- 你發現自己在解釋為什麼錯誤訊息「其實沒關係」。
- 任務需要跨 3 個以上模組同時推理，或牽涉你沒把握的領域知識。
- 這是品味/設計題（好幾個都能跑的方案要選一個），而你只能列選項、講不出決定性理由。

**正例**：sonnet 修 DI 註冊 bug，兩次修改後測試都掛在同一個 resolution error → 停手，帶兩次的 diff 與錯誤原文升級 opus。
**反例**：測試掛在 A，改完換掛在 B——這是**進展**不是重複失敗，不用升級，繼續。

## 2. 何時算真的完成

「完成」= 以下全部成立，缺一項就不能宣稱完成：

1. 驗收條件逐條核對過，每條有**實際執行的證據**（測試輸出原文、read-back 結果），不是推論。
2. 驗證是 fresh-context agent 或實際命令做的，不是作者自己的判斷（見 `model-dispatch.md` §6）。
3. 沒有被默默跳過的步驟。跳過的事（某測試沒跑、某平台沒驗）必須明說。

**正例**：「完成。`dotnet test` 全過（37 passed，輸出如下），read-back agent 確認 3 個檔案內容符合規格。未驗：Windows 環境。」
**反例**：「已完成修改，邏輯上應該能正確處理所有情況。」——「應該」就是沒驗，不算完成。

## 3. 何時該停下來問使用者

以下情況**必須停**，不能自己選一個做下去：

- 兩個合理方案會導致**不同的對外行為**（API 格式、使用者可見行為、資料 schema）。
- 要做**難以回滾**的事：刪資料、force push、改共用設定、對外發送（留言、寄信、發 MR comment）。
- 發現需求和 codebase 現實矛盾（使用者要的東西建立在錯誤前提上）。
- 品味/取捨題且兩邊都有實質代價。

以下情況**不要問**，自己決定並在回報中說明：

- 純內部實作選擇（private method 怎麼拆、變數命名）。
- 有慣例可循的選擇（照 codebase 既有 pattern）。限風格與可逆的實作選擇；若既有 pattern 本身技術正確性可疑，適用 `engineering.md` 的「第一性原理 > status-quo 一致性」，不受此條約束。
- 可逆且成本低的選擇（先做 A，錯了換 B 的代價 < 一次來回問答）。

**正例（該問）**：遷移 API 時發現舊 endpoint 有個未文件化的 query param，有兩個下游在用——保留還是趁機砍掉？→ 問。
**反例（不該問）**：「請問我要用 for 迴圈還是 LINQ？」→ 自己選，照周圍 code 的慣例。

## 4. 什麼訊號代表方向錯了，該換路而非重試

重試 = 同方法再來一次；換路 = 換方法/換切入點。出現以下訊號時重試是浪費：

- **修好 A 壞 B、修好 B 壞 A**：兩個補丁互相打架 → 問題在更上層的設計，停止打補丁，回頭看架構。
- **workaround 疊 workaround**：第二層 workaround 出現時，第一層就是錯的。
- **每一步都比預期難**：預估 30 分鐘的事做了三倍時間還在處理前置問題 → 這條路的前提可能錯了。
- **開始對抗工具**：需要繞過 framework/linter/型別系統才能繼續 → 工具在告訴你設計錯了。

**正例**：為了讓測試過而 mock 越加越多，第 4 個 mock 出現 → 停，重新看被測物的依賴設計是不是該拆。
**反例**：編譯錯誤改一個少一個 → 正常收斂中，不是換路訊號，繼續。

## 5. 品質底線怎麼驗（最低標準，不可再降）

- **任何程式碼變更**：至少實跑一次受影響的路徑（測試、或實際執行該功能）。編譯過 ≠ 驗過。
- **任何 script**：用 production 實際的 interpreter 跑過（macOS `/bin/bash` 是 3.2，不代表 CI 環境）。
- **任何檔案交付**：read-back 確認落地且完整。
- **任何「我查過了」的宣稱**：要有查證的實際輸出（grep 結果、文件段落），沒有輸出就重查。
- **不確定的事**：標註「未驗證」交出去，永遠優於裝作驗過。錯誤的自信是最貴的錯。

## 6. 模糊題與品味題的誠實處理

這套 rubric 補不了需求模糊與品味判斷（見 `diagnosis.md` 誠實條款）。遇到時按順序：

1. 先確認是不是真模糊：能不能從 code、文件、git history 找到答案？派 agent 查完再說。
2. 查不到且影響對外行為/架構 → 停下來問使用者（§3）。
3. 使用者不在且必須前進 → 選**最可逆**的方案，把決策與理由顯式記錄在回報裡，標明「此處是我的判斷，可推翻」。
