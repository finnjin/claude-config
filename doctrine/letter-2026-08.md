## 三件我沒被問、但認為最重要的事

### 1. 制度要用數據關帳，不是用感覺續約

今晨（2026-08-08）的 P1–P4 修法在本信寫下時全部未經下游 session 驗證。約 4–6 週後（2026-09 中），派一個 agent 照 `diagnosis-2026-08.md`「驗證方式」節重算四個指標：depth≥2 派工數（目標≈0）、主對話 Bash/Edit/Read 次數（應下降）、低風險變更的 verifier 開設率（應下降）、直接派工 p90 時長（應 <20 分鐘）。任何指標沒改善，對應規則就是失敗的——改掉或刪掉，不要留著當裝飾。這件事是機械性重算＋對照目標值，Sonnet 等級做得動。

### 2. 停用的東西要拆乾淨，不要長期靠路由對沖

/cr 系列與部分停用 skill 仍掛在每 session 的清單裡自我宣傳（現況與具體檔案清單見 `diagnosis-2026-08.md` 補記 #2），目前只靠 CLAUDE.md 一行路由擋著。弱模型對「單一指令跑完全流程」這種措辭抵抗力低，路由對沖會退化。需要船長決定的順序：先把 commands/skills 納入版控（擴 claude-config 白名單或另立 repo），再實際刪除停用項。superpowers ablation 同理：若幾週後除錯品質可觀察退化，憑證據決定是否引入對應流程，不要憑懷念裝回。

### 3. 機制事實與判準分離，是這套制度活下去的關鍵

harness 比 doctrine 改得快——單是 2026-08-08 一天，主對話工具面就出現了 Workflow、ScheduleWakeup、內建 memory 協議等 doctrine 沒寫過的元素。分工原則：**判準**（勞動/理解分類、驗證分級、升降級路徑）跨版本穩定，寫在各章節；**機制事實**（enum、預設值、工具名）只集中在 `model-dispatch.md` §9，且 schema 優先——當下工具 schema 與快照矛盾時照 schema 行動並更新快照。未來往 doctrine 寫任何東西前先問一句：這是判準還是機制事實？機制事實不准散進判準章節，散了就會過期在抓不到的地方。

2. **雙源漂移**（新增）：同一教訓在 memory 與 doctrine 各記一份，之後改了一邊忘了另一邊，兩份權威互相矛盾。預防：教訓一般化進 doctrine 後，memory 條目縮成一行指標指向 doctrine（`feedback_no_pointless_defensive` 的「已一般化為 doctrine 規則」寫法是正例，照抄）。
